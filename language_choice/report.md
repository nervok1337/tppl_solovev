# Выбор парадигм и языков программирования

## 1. Обработка больших данных в реальном времени

**Парадигма:** императивная процедурная с параллельной обработкой данных.

**Основной язык программирования:** C++.

**Альтернативы:** Rust, C, CUDA C++.

**Обоснование:** один кадр занимает около 32 МБ, поэтому при 100 кадрах в секунду системе необходимо обрабатывать примерно 3,2 ГБ данных в секунду. C++ обеспечивает высокую производительность, прямое управление памятью, многопоточность и поддержку библиотек OpenCV, Intel oneTBB и CUDA. Процедурная парадигма позволяет представить обработку как последовательность этапов, а параллельность — одновременно принимать и анализировать кадры. Rust является более безопасной альтернативой для системы, работающей круглосуточно, но обладает менее зрелой экосистемой для обработки изображений и GPU. C даёт полный контроль, однако усложняет разработку и безопасное управление памятью. Python, тяжёлое объектно-ориентированное проектирование и разделение каждого этапа на отдельный микросервис будут излишними из-за накладных расходов и высокой нагрузки.

## 2. Прототип ML-сервиса для прогноза погодных условий

**Парадигма:** процедурная с элементами объектно-ориентированного программирования.

**Основной язык программирования:** Python.

**Альтернативы:** R, Julia, Java/Kotlin.

**Обоснование:** прогноз выполняется только один раз в сутки, поэтому максимальная производительность не является главным требованием. Python позволяет создать MVP за короткий срок, быстро менять алгоритмы и использовать готовые библиотеки: pandas, NumPy, scikit-learn, PyTorch, XGBoost и FastAPI. Процедурный подход удобен для последовательности «получение данных — обработка — прогноз — сохранение результата», а ООП можно применять для моделей и источников данных. R подходит для статистического анализа, Julia — для быстрых математических вычислений, а Java или Kotlin — для интеграции с JVM-системами, но разработка прототипа на них обычно занимает больше времени. C++, сложная микросервисная архитектура и написание собственных ML-алгоритмов будут излишними для MVP.

## 3. Интерактивный UI для торгового терминала

**Парадигма:** реактивная и событийно-ориентированная с элементами функционального программирования.

**Основной язык программирования:** TypeScript.

**Альтернативы:** JavaScript, Dart, Elm.

**Обоснование:** интерфейс должен реагировать на действия пользователя, сообщения WebSocket, ответы REST API и изменения связанных виджетов. Реактивная парадигма позволяет автоматически обновлять только зависимые части интерфейса, а функциональный подход делает изменение состояния предсказуемым и удобным для тестирования. TypeScript добавляет строгую типизацию и помогает контролировать сложные структуры данных, сохраняя доступ к экосистеме React, Vue, Angular и RxJS. JavaScript проще для быстрого старта, но менее безопасен в большом проекте. Elm предлагает строгий функционально-реактивный подход, а Dart удобен вместе с Flutter Web, однако их экосистемы меньше. Ручное обновление DOM, один глобальный объект состояния и отдельный микрофронтенд для каждого виджета излишне усложнят систему. Для реакции быстрее 16 мс также потребуются пакетная обработка событий и сокращение лишних перерисовок.

## 4. Прошивка для устройства регистрации температуры

**Парадигма:** императивная процедурная.

**Основной язык программирования:** C.

**Альтернативы:** Rust, C++.

**Обоснование:** C создаёт компактные программы, почти не требует среды выполнения и предоставляет прямой доступ к GPIO, ADC, UART и другим регистрам микроконтроллера. Процедурная парадигма подходит для последовательности «инициализация — ожидание — измерение — передача — сон» и обеспечивает предсказуемое время выполнения. Для переносимости обращения к конкретному оборудованию следует вынести в отдельный аппаратно-зависимый слой HAL. Rust повышает безопасность работы с памятью, но поддерживается не всеми микроконтроллерами и инструментами. C++ позволяет создавать удобные абстракции, однако требует отказа от тяжёлых возможностей языка. Python, Java, C#, динамическое выделение памяти, сложное ООП и RTOS при отсутствии нескольких независимых задач будут излишними при ограничениях в 256 КБ Flash и 32 КБ RAM.
